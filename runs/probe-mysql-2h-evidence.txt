1. The collation half of the CONFORMANCE failures
-------------------------------------------------
Reason to run it: the graph-conformance oracle reported CONSTRAINT_TOO_STRICT because it planned two
rows whose UNIQUE / PRIMARY KEY values differ only in case, and MySQL refused the second one with
1062. If that is the explanation, the oracle's duplicate check (case-sensitive, like Java's String
comparison and like the embedded engines' default text comparison) and the engine's (case-insensitive
by default) disagree.

2. The foreign-key half: is a NULL in a neighbouring column enough to skip the check?
-----------------------------------------------------------------------------------
Reason to run it: the constraint-enforcement oracle reported CONSTRAINT_NOT_ENFORCED - a child row
whose foreign key value has no parent (t_3_id = 9223372036854775806) was stored. The child table also
carried `CREATE UNIQUE INDEX uidx_t_4_0 ON t_4 (t_3_id, t_2_id, id)`, and the inserted row left
t_2_id NULL. The filed defect bugs/mysql/002 says a *non-unique* index whose leading column is the
foreign key column becomes the index the check is made with, and that a NULL in ANY column of that
index then satisfies the check - but its measurement table records UNIQUE (f1, other) as still
enforced. The matrix below measures both shapes, on both foreign-key paths.

p.k = 1, every insert carries the dangling f1 = 999, so ACCEPTED means the engine stored a child row
whose parent does not exist.

$ bash probe-mysql-2h-fk-index-matrix-run.sh ddlsmith-2h-mysql:ddlsmith_fkmain

What the two blocks say together:

  * the skip needs a multi-column index that leads with the foreign key column AND a NULL in one of
    its other columns: `UNIQUE (f1)` with other = NULL is still enforced;
  * uniqueness does not save it - `UNIQUE (f1, other)` is skipped exactly like `INDEX (f1, other)`,
    which contradicts the "UNIQUE (f1, other) -> rejected 1452" row of bugs/mysql/002 and means the
    mitigation that report records does not hold;
  * the same six cases are all enforced when the server runs the InnoDB path
    (`innodb_native_foreign_keys=TRUE`), on the same image and the same version, so the skip belongs to
    the SQL-engine foreign-key path MySQL 9.6 introduced - the same place as bugs/mysql/001..004.
